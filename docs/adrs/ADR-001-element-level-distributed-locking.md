# ADR-001 — Element-Level Distributed Locking in Distributed Slides

- **Status:** Accepted for the prototype (design decision; implementation pending)
- **Date:** 2026-11-22
- **Scope:** Presentations in `SHARED` mode; collaborative editing of text and shapes
- **Priority:** Essential for collaborative editing; renewal and automatic expiration are part of this design, but their implementation is assigned to Stage C
- **Dependency:** Correct Raft replication across at least three replicas
- **Related documents:** `project-proposal.md`, User Story 01, `CMP5001-Proyecto.pdf`, `cmp5001-proyecto-starter.zip`

## 1. Context and problem

Sofia creates a presentation in `PRIVATE` mode and edits it without distributed locks, because her device is its sole authority. Once she publishes it, the presentation enters `SHARED` mode and the Raft cluster becomes authoritative for shared modifications.

In shared mode, Sofia and Santiago may edit **different elements** concurrently. They must not both successfully commit incompatible changes to **the same element**. The interface should show who has selected/is editing an element and prevent another session from editing it. Correctness must not depend on every browser receiving a notification at the same instant: authority belongs to the replicated state machine.

The design must also recover abandoned locks after disconnections, tolerate leader failures, retries, network partitions, and delayed messages, and reject updates from clients whose locks have already been invalidated.

## 2. Decision

**Use exclusive, selection-triggered, per-element locks replicated as commands of a single Raft state machine.**

1. **`SHARED` mode only.** Operations in `PRIVATE` mode are local and do not require distributed locking.
2. **Selection signals an intent to edit.** Selecting an existing text element or shape triggers `acquire_lock`. The UI may show selection while the request is pending but **must not permit a confirmed shared edit** until acquisition succeeds. Deselecting, moving focus, or closing the editor triggers `release_lock`.
3. **Atomic creation with selection.** `create_element` creates the element **and acquires its initial lock in one Raft entry**. It does not require an earlier slide-wide structural lock. The creator initially selects the new element. Duplicate element IDs are rejected; the Raft log determines the order of concurrent insertions.
4. **Granularity.** A lockable resource is `(deck_id, element_id)`. Different resources can be edited by different sessions. There is no global slide lock in the initial scope.
5. **Protected writes.** `update_element` and `delete_element` require the owning session, its current lock token, and the expected element version. These checks occur **atomically during application of the committed command**.
6. **Renewal and expiration.** While selected, the client periodically requests `renew_lock`. The leader tracks inactivity with its **local monotonic clock** and may propose `expire_lock`, but both renewal and expiration become effective **only once committed and applied through Raft**. Followers do not independently expire locks.
7. **Fencing tokens.** Each successful acquisition receives an integer `fencing_token` that increases **per resource**, generated by the replicated state machine. A former owner cannot reuse a token after release, expiration, or a newer acquisition.
8. **UI reads.** `get_element`, `get_slide`, and `read_lock_status` may return eventually consistent local replica state; they never authorize a write. Only committed lock operations and the checks performed when applying an edit can establish editing authority.
9. **Success responses.** A server acknowledges a lock or modification only after applying its committed log entry; sending the command or storing it on one replica is insufficient.

### 2.1. Decision for `create_element`

A lock such as `slide-X:structure` is **not required** merely to add a shape or text box. It would unnecessarily serialize additions to the whole slide. This decision supersedes the preliminary structural-lock suggestion in `project-proposal.md` for simple element creation.

Santiago's first distributed operation when creating an element is:

```text
create_element(deck_id, slide_id, element_id, type, initial_properties)
  [single Raft log entry]
  -> validate deck/slide and uniqueness of element_id
  -> insert element with version = 1
  -> create an exclusive element lock owned by the requesting session
  -> assign fencing_token = 1
  -> return CREATED_AND_LOCKED
```

The operation is indivisible: **there is no observable committed state in which the element has been created but its creator has not yet acquired its initial lock**. Another client could temporarily see an outdated preview before receiving a lock notification, but it cannot obtain authoritative ownership or modify the new element through the current leader.

Multiple `create_element` operations for different elements on the same slide may run concurrently and are ordered by Raft. The initial visual stacking order is committed insertion order unless a later feature defines `z_index` and explicit reordering. **Slide creation, deletion, and reordering are Stage B scope but remain outside this element-locking ADR**; they require a separate structural-version decision.

## 3. Identifiers, versions, and total order

These concepts are distinct; **none can substitute for another**.

| Concept | Generation | Purpose | Defines execution order? |
|---|---|---|---|
| `deck_id`, `element_id` | Complete UUIDv4 on object creation | Stable object identity; collision avoidance | No |
| `session_id` | Complete UUIDv4 per editor session | Identify a session and associate ownership/requests | No |
| `request_id` | Complete UUIDv4 per logical editor operation; reused for retries | Deduplication and idempotence | No |
| `local_op_id` | `(installation_uuid, local_counter)` | Private-mode local operation journal | Only within that installation |
| `version` | Per-element integer incremented for committed edits | Reject stale `expected_version` | No; it is an object revision |
| `fencing_token` | Persistent per-element integer incremented on each new acquisition | Reject stale lock owners | Orders acquisitions **of that resource**, not all commands |
| `lease_epoch` | Counter for the active lock, incremented on renewal | Invalidate stale expiration proposals | No |
| Raft log position | Log index and term assigned through Raft | **Authoritative total order** for shared commands | **Yes** |

**Regarding `8 UUID bits + operating system + another 8 bits`:** the operating system name does not supply reliable random entropy. Such an ID would have, at most, 16 random bits and a high collision probability (approximately 50% after around 300 independent samples). A complete UUIDv4 provides 122 random bits under RFC 9562. If useful for diagnostics, the operating system can be stored as **separate metadata** rather than used to decide lock ownership or break ordering ties.

**UUIDs do not break linearizability ties.** When Sofia and Santiago send concurrent commands, Raft chooses one committed log order. That order, not lexical UUID order or a predetermined client order, determines which operation succeeds. Client IDs do not need to be known in advance.

The starter's `client.py` generates `req.id` from a client label and eight hexadecimal UUID digits (32 random bits). This is adequate for small course scenarios but less robust than a complete UUIDv4. We will not alter the starter solely to change this convention. A future web client should use complete UUIDv4 request IDs, and `app.py` must accept both formats without interpreting their contents.

## 4. Persistent state model

Replicated presentation state includes:

```json
{
  "decks": {
    "deck-1": {
      "slides": {
        "slide-1": {
          "elements": {
            "element-1": {
              "type": "text",
              "properties": {"text": "Introduction"},
              "version": 3,
              "deleted": false
            }
          }
        }
      },
      "locks": {
        "element-1": {
          "status": "HELD",
          "owner_session": "santiago-session",
          "fencing_token": 4,
          "lease_epoch": 2
        }
      },
      "fencing_counters": {"element-1": 4}
    }
  },
  "request_results": {}
}
```

- `locks` and `fencing_counters` are **authoritative replicated state**, not leader-only caches.
- `fencing_counters` **never decrease** on release/expiration. Deleted element IDs remain as tombstones and **are not reused**.
- `FREE` may be represented by the absence of an active lock record; the fencing counter must still be retained.
- Deduplication results are indexed by `(req.client, req.id)` and store a canonical fingerprint of `(op, args)`. Reuse of the same request ID with different content yields `REQUEST_ID_REUSE` without applying another mutation.
- Element versions increase on `update_element` and `delete_element` as defined by the state model; **not** on `acquire_lock`, `renew_lock`, `release_lock`, or `expire_lock`. `delete_element` should increment the version and set `deleted=true`.
- Activity timers and deadlines **are not deterministic replicated state**. Only the leader maintains ephemeral timers for proposing expiration.
- Confirmed state and deduplication results survive restarts through the log and/or a consistent state-machine snapshot. **Do not respond before performing the durability steps required by Raft.**

## 5. Lock state machine

```text
        acquire_lock / create_element
   FREE --------------------------------> HELD(token=N, lease_epoch=0)
     ^                                       |          |
     |                                       |          +-- valid renew_lock
     |                                       |              HELD(token=N, epoch+1)
     |                                       |
     +------------ valid release_lock -------+
     +------------ committed expire_lock ----+
     +------------ valid delete_element -----+
```

A resource remains **HELD** until a committed entry changes that state. The passage of time on a client, or a missed heartbeat message, does not independently change the replicated state.

### 5.1. UI behavior

- **Select an existing element:** display `PENDING_LOCK`; send one `acquire_lock` for the attempt; do not save shared changes before `LOCK_ACQUIRED`.
- **Lock granted:** display `EDITING` and the owner; allow local editing and `update_element` using the token and expected version. Other sessions display `LOCKED_BY_OTHER` when they next synchronize; even with stale UI, the server rejects invalid acquisitions or edits.
- **Lock denied:** show the owner when known and keep the element `READ_ONLY`; do not change authoritative content.
- **Deselect/blur/switch elements:** request `release_lock` if the session owns the token. Do not block the visual selection change while waiting for the release response; the previous lock may remain until release or expiration commits.
- **Connectivity lost or renewal outcome uncertain:** mark editing `UNVERIFIED` and keep unsaved changes as a local draft. Do not claim the lock is valid or that an edit has been saved.
- **Create an element:** show a `PENDING_CREATE` draft; send `create_element` (creation plus lock). Do not present it as shared until `CREATED_AND_LOCKED`. If it was deselected while pending, release its token immediately after a successful response.
- **Unexpected close:** releasing the lock is best-effort; expiration handles abandonment.

Other clients learn about locks through **polling** applied state in the first implementation; WebSockets are not necessary. UI notification is eventual and is not a safety mechanism.

## 6. Command contracts

All distributed commands carry `deck_id`; element operations additionally carry `element_id`. In the prototype, `req.client` identifies a logical session and `req.id` identifies a logical operation. Real authentication is out of scope: **a session name and a fencing token are not security credentials**.

| Command | Additional arguments | Preconditions at committed application | State transition | Application result |
|---|---|---|---|---|
| `create_element` | `slide_id`, `element_id`, `type`, `properties` | Deck/slide exist; `element_id` has never been used | Create at version 1; fencing counter becomes 1; create HELD for `req.client` at epoch 0 | `CREATED_AND_LOCKED`, `version=1`, `fencing_token=1` |
| `acquire_lock` | — | Element exists, is not deleted, and is FREE | Increment fencing counter; create HELD for `req.client`, epoch 0 | `LOCK_ACQUIRED`, `fencing_token`, `version` |
| `renew_lock` | `fencing_token` | HELD by `req.client` with matching token | Increment `lease_epoch`; refresh the current leader's ephemeral timer on application | `RENEWED`, `lease_epoch` |
| `update_element` | `fencing_token`, `expected_version`, `patch` | Lock matches session/token; element is active; version matches | Apply permitted patch and increment version | `SAVED`, `version` |
| `release_lock` | `fencing_token` | HELD by `req.client` with matching token | Remove active lock; retain fencing counter | `RELEASED` |
| `delete_element` | `fencing_token`, `expected_version` | Same guards as an update | Set `deleted=true`, increment version, release lock, keep tombstone and counter | `DELETED`, `version` |
| `expire_lock` | `expected_token`, `expected_lease_epoch` | HELD with both fields matching | Remove active lock; retain fencing counter | `EXPIRED` or `NO_OP_STALE_EXPIRY` |

**`expire_lock` is internal.** Only the leader proposes it from `on_tick`; it must not be exposed as a public command that any session can invoke. A future `force_unlock` requires independent permission checks and a separate scope decision.

**Repeated acquisition by the owner:** If an `acquire_lock` arrives with a *new* request ID and that same session already owns the element, return `ALREADY_HELD` with the existing token, **without incrementing** fencing or renewing. If the *same* request ID is retried, deduplication returns exactly the previous result. Renewal is always explicit.

**Edit patches:** Initially permit only replacements of supported text, style, position, and size fields. Do not execute arbitrary HTML. Validate types and bounds before log proposal, and recheck state-dependent preconditions on committed application. The committed command contains canonical data; application code must not consult clocks, generate randomness, or make network calls.

### 6.1. Responses and errors

The starter distinguishes **business-level rejection** from **infrastructure failure**:

```json
{"ok": true, "result": {"status": "LOCKED", "owner_session": "sofia-session"}}
```

An occupied lock, stale token, wrong version, deleted element, or reused ID is a **valid application response** (`ok:true` with a rejection status). State-dependent command results should follow the Raft order when concurrency matters and be recorded for deduplication.

```json
{"ok": false, "error": "QUORUM_UNAVAILABLE"}
```

A leader without a majority must **not** claim to have granted a lock or saved an edit. It may leave the request pending until the runtime times out, or return `ok:false` for a retry. A follower may return `{"redirect": "n2"}` if it knows the leader, but cannot authorize commands itself.

Relevant application statuses: `CREATED_AND_LOCKED`, `LOCK_ACQUIRED`, `ALREADY_HELD`, `LOCKED`, `RENEWED`, `RELEASED`, `EXPIRED`, `SAVED`, `DELETED`, `NOT_FOUND`, `VERSION_CONFLICT`, `STALE_TOKEN`, `NOT_OWNER`, `REQUEST_ID_REUSE`, `INVALID_ARGUMENT`.

### 6.2. Deterministic application pseudocode

```python
# Run once per COMMITTED Raft entry, in the same order on every replica.
def apply_command(state, cmd, session, request_id):
    dedup_key = (session, request_id)
    fingerprint = canonical_fingerprint(cmd)
    previous = state.request_results.get(dedup_key)
    if previous is not None:
        if previous.fingerprint != fingerprint:
            return {"status": "REQUEST_ID_REUSE"}
        return previous.result

    resource = get_resource(state, cmd.deck_id, cmd.element_id)

    if cmd.op == "create_element":
        result = create_and_lock_atomically(state, cmd, session)

    elif cmd.op == "acquire_lock":
        if not resource.exists or resource.deleted:
            result = {"status": "NOT_FOUND"}
        elif resource.lock is not None:
            result = ({"status": "ALREADY_HELD", "fencing_token": resource.lock.token}
                      if resource.lock.owner == session
                      else {"status": "LOCKED", "owner_session": resource.lock.owner})
        else:
            resource.fencing_counter += 1
            resource.lock = Lock(owner=session, token=resource.fencing_counter, lease_epoch=0)
            result = {"status": "LOCK_ACQUIRED", "fencing_token": resource.lock.token,
                      "version": resource.version}

    elif cmd.op == "renew_lock":
        if not matching_owner_and_token(resource.lock, session, cmd.fencing_token):
            result = {"status": "STALE_TOKEN"}
        else:
            resource.lock.lease_epoch += 1
            result = {"status": "RENEWED", "lease_epoch": resource.lock.lease_epoch}

    elif cmd.op == "update_element":
        if not matching_owner_and_token(resource.lock, session, cmd.fencing_token):
            result = {"status": "STALE_TOKEN"}
        elif resource.version != cmd.expected_version:
            result = {"status": "VERSION_CONFLICT", "current_version": resource.version}
        else:
            apply_validated_patch(resource, cmd.patch)
            resource.version += 1
            result = {"status": "SAVED", "version": resource.version}

    elif cmd.op == "release_lock":
        if not matching_owner_and_token(resource.lock, session, cmd.fencing_token):
            result = {"status": "STALE_TOKEN"}
        else:
            resource.lock = None
            result = {"status": "RELEASED"}

    elif cmd.op == "expire_lock":
        if (resource.lock is not None and
            resource.lock.token == cmd.expected_token and
            resource.lock.lease_epoch == cmd.expected_lease_epoch):
            resource.lock = None
            result = {"status": "EXPIRED"}
        else:
            result = {"status": "NO_OP_STALE_EXPIRY"}

    else:
        result = {"status": "UNKNOWN_OPERATION"}

    state.request_results[dedup_key] = StoredResult(fingerprint, result)
    return result
```

This pseudocode omits type validation and `delete_element` to highlight the invariants. Production code must check resource existence before accessing fields and must handle internal `expire_lock` separately from client deduplication. **Variable timestamps and Raft commit indices should not be added to results compared by `spec.py` unless its reference model can reproduce them.**

## 7. Renewal, expiration, and leader changes

### 7.1. Proposed configuration

| Setting | Initial value | Note |
|---|---:|---|
| `LOCK_INACTIVITY_TIMEOUT` | 10 s | Time without committed activity before **proposing** expiration; not a precise global deadline |
| `LOCK_RENEW_INTERVAL` | 3 s | Client requests renewal while element remains selected |
| `TICK` | 50 ms | Provided by `node.py`; does not imply 50 ms expiration precision |
| `CLIENT_WAIT` | 5 s | HTTP request waiting limit inside `node.py` |

A ±10 ms renewal tolerance is not used. In an asynchronous system, delays, process pauses, and leader elections invalidate that precision assumption.

### 7.2. Leader algorithm

1. When the current leader **applies** a committed acquisition or renewal, record ephemeral `last_activity_monotonic[(deck_id, element_id, token, lease_epoch)] = self.now()`.
2. When `on_tick` observes more than 10 seconds of inactivity, propose **one** `expire_lock(deck_id, element_id, expected_token, expected_lease_epoch)` entry for that lock generation. Keep an ephemeral in-flight marker to prevent proposal storms.
3. At application time, every replica checks **only** `(token, lease_epoch)`. If a prior renewal changed the epoch, expiration is `NO_OP_STALE_EXPIRY`. If expiration wins the Raft order, a later renewal fails with `STALE_TOKEN`.
4. A new leader reconstructs ephemeral timers and **waits a full fresh grace period** before proposing expiration for inherited locks; it does not interpret another node's monotonic timestamps. An expiration already present in the previous log may nevertheless commit: the post-failover grace period is a **proposal policy**, not an absolute promise that no locks will expire during that interval.
5. Only a leader with a majority may commit expiration. Neither isolated leaders nor followers expire locks unilaterally.

**Chosen semantics:** leader-managed inactivity expiration, *not* a globally synchronized lease deadline. Expiration is not promised at exactly 10 seconds; exclusivity, fencing, and eventual recovery of abandoned resources under a stable majority are the guarantees.

### 7.3. Renewal-versus-expiration race

```text
Initial state: HELD(token=7, lease_epoch=2)

Raft order A:
  renew_lock(token=7)           -> epoch=3, RENEWED
  expire_lock(token=7, epoch=2) -> NO_OP_STALE_EXPIRY
  Result: lock remains HELD.

Raft order B:
  expire_lock(token=7, epoch=2) -> EXPIRED
  renew_lock(token=7)           -> STALE_TOKEN
  Result: lock is FREE; next acquisition receives token=8.
```

The race is resolved **without** global timestamps or UUID comparisons.

## 8. Behavior under failures

| Situation | Allowed behavior | Preserved invariant |
|---|---|---|
| Two clients select the same element | One acquires; the other receives `LOCKED` (or `ALREADY_HELD` for the same session) | At most one current owner per element |
| Two clients create different elements | Each can commit in its own log entry and acquire its new element | No global slide lock |
| Follower fails | Leader and surviving follower continue committing | Majority of 2/3 |
| Leader fails after acknowledging acquisition | A newly elected leader retains the committed acquisition | No confirmed lock is lost |
| Leader fails before responding | Outcome is uncertain; retry the **same** request ID | Deduplication prevents duplicate application |
| Network partitions 1/2 | Minority: local reads, no confirmed writes. Majority: commits and expirations possible | No conflicting authoritative lock grants |
| Owner is isolated on minority side | May keep a local draft; cannot confirm update or renewal | Majority can expire/reassign; old token rejected |
| Renewal arrives after expiration | `STALE_TOKEN` | No resurrection of expired locks |
| Old release arrives after a new acquisition | Rejected because token no longer matches | New owner remains protected |
| Lagging follower rejoins | Applies missing log entries before claiming current state | Convergence to same replicated state |
| Two replicas fail | No majority; no new write confirmations | Safety at the expense of availability |

**Important boundary:** if a replica restarts with its disk erased, losing Raft vote/term metadata may break a simplistic Raft recovery model. The final project must state its failure assumptions and either implement safe reintroduction or explicitly exclude this from its safety model.

## 9. Testable guarantees and invariants

1. **Exclusion:** Each committed state has at most one active owner per `(deck_id, element_id)`.
2. **Linearizable transitions:** `create_element` (including initial lock), `acquire_lock`, `renew_lock`, `release_lock`, `expire_lock`, `update_element`, and `delete_element` follow one committed application order.
3. **No authority from eventual reads:** Observing `FREE` on a stale follower does not authorize an acquisition or edit without a commit.
4. **Safe editing:** `update_element` changes content only if owner, token, and `expected_version` match at application time.
5. **Persistent fencing:** Once lock generation N is released or expires and N+1 is granted, N cannot edit the element or release N+1.
6. **Correct renewal:** An expiration with an older `expected_lease_epoch` cannot invalidate a lock that was renewed earlier in the Raft order.
7. **No duplicate mutation:** Retrying identical content with the same `request_id` returns the prior result without a second creation, update, or renewal.
8. **No false commits:** An isolated replica cannot return `LOCK_ACQUIRED`, `SAVED`, or `RENEWED` when the corresponding entry has not committed.
9. **Convergence:** After the network heals and writes stop, replicas eventually apply the same element content, versions, locks, and fencing counters.
10. **Conditional progress:** With a stable majority, stable leader, eventual message delivery, and ticks, an abandoned lock eventually becomes eligible for expiration and later acquisition. No bounded completion time is guaranteed during arbitrary failures.

## 10. CMP5001 starter integration

- **`app.py`:** implement Raft and the state machine. `start()` restores durable state; `on_request(req)` directs requests toward the leader and tracks pending ones; `on_message(src, msg)` processes Raft traffic; `on_tick()` performs heartbeats/elections and checks expirations **only on the leader**; `status()` exposes `role` and `term`.
- **Persistence:** use `self.disk` / `self.save()` for terms, votes, log, and consistent state-machine data/snapshot. Persist required information **before** confirming operations.
- **`req.client`:** logical session for course scenarios, **not** proof of real identity. `req.id` is the request ID. Store deduplication results in replicated state so they survive a leader change.
- **Deferred replies:** If an entry is not committed yet, `on_request` may return `None`, then call `self.reply(req.id, response)` after application. A leader that loses its majority cannot confirm the result.
- **`spec.py`:** define linearizable operations, eventual operations (`get_element`, `get_slide`), and deterministic sequential `apply`. Use a key that encompasses the relevant lock and element state (the `deck_id` is sufficient for a small prototype). Eventual reads can be checked for convergence when paired with `client.final()`.
- **`check.py` caveat:** Internal automatic expirations may not appear in the histories produced by `client.py`. Therefore, the generic checker cannot necessarily reconstruct all time-driven transitions. Run core checker scenarios without unrecorded expirations affecting checked keys, and add a **separate targeted expiration/renewal test**, or extend history instrumentation without inventing user operations. Do not represent a partial checker pass as full proof of the timing protocol.
- **No extra replication dependencies:** Python 3.11+ and the standard library. Do not use libraries that implement distributed consensus, merging, or locking on the project's behalf.

## 11. Acceptance cases for the implementation agent

| ID | Setup and trigger | Required result |
|---|---|---|
| L-01 | Sofia and Santiago simultaneously call `acquire_lock` for E1 | Exactly one `LOCK_ACQUIRED`; competing session receives `LOCKED` |
| L-02 | Sofia locks E1; Santiago locks E2 | Both succeed; independently edit different elements |
| L-03 | Santiago calls `create_element` for E3 | E3 appears at version 1 and **already locked** by Santiago in the same commit |
| L-04 | A client without the token edits E1 | `STALE_TOKEN`; element version unchanged |
| L-05 | Owner edits E1 with an old version | `VERSION_CONFLICT`; content/version unchanged |
| L-06 | Owner renews before an expiration for the previous epoch applies | `NO_OP_STALE_EXPIRY`; ownership retained |
| L-07 | `expire_lock` commits before renewal | Lock expires; late renewal rejected; next acquisition gets a larger token |
| L-08 | An old-token `release_lock` arrives after reacquisition | Does not release the new owner's lock |
| L-09 | `create_element` / `update_element` retried with same `request_id` | Same result; only one logical mutation |
| L-10 | Kill leader during `acquire_lock`, then retry | No confirmed ownership is lost or incompatible grants returned |
| L-11 | Partition `n1 / n2,n3` | Minority cannot commit; majority can grant/renew/expire subject to state |
| L-12 | Isolate owner; allow majority to expire/reassign; heal | Old token rejected; all replicas converge to new owner/state |
| L-13 | Kill follower, continue editing, restart it | Recovers log and element/lock state |
| L-14 | Lose two replicas | No new edits can be confirmed |
| L-15 | Deselect/blur while `release_lock` is interrupted | UI does not falsely claim release; eventually release or expiration |
| L-16 | Change leader while a renewed lock is held | New leader rebuilds timer; no invalid token can edit |

**Required cost comparison for the course:** compare p50/p95 latency for `acquire_lock` or `update_element` (Raft majority) versus `get_element` (eventual local read), and measure periods without responses during partition or election.

## 12. Suggested implementation order

1. Implement durable element, lock, fencing counter, version, and deduplication state.
2. Implement atomic `create_element`, `acquire_lock`, `update_element`, and `release_lock` as a **standalone sequential state machine** and test it before integrating Raft.
3. Connect deterministic application to committed Raft log entries, persistence, and after-commit responses; implement an equivalent `spec.py` model.
4. Test concurrency, retries, failover, partition, and recovery with expiration disabled.
5. In **Stage C**, add `renew_lock`, `lease_epoch`, and `expire_lock` with leader-only monotonic timers; test renewal/expiration races and failover.
6. Connect UI states: selection, `PENDING_LOCK`, editing, polling, renewal, deselection/release, and unsaved drafts.
7. Record scenario histories, run `check.py`, and document the supplementary expiration tests.

## 13. Rejected alternatives and consequences

| Alternative | Decision and reason |
|---|---|
| Slide-wide structural lock for every creation | **Rejected** for initial scope: atomic `create_element` need not change other elements and a global lock would add unnecessary contention |
| Create element, then acquire lock in two separate operations | **Rejected**: permits another client to acquire the newly created element in between |
| Sort commands by UUID or device ID | **Rejected**: does not establish actual commit order or solve concurrent requests; Raft orders commands |
| Truncated UUIDv4 with 8+8 bits and OS name | **Rejected** as a global identifier because of collisions; OS may be optional metadata |
| LWW CRDT as authority for content and locks | **Rejected**: does not provide conditional exclusive acquisition; the Raft log already orders authorized modifications |
| Renewal only in leader memory | **Rejected**: a replacement leader might not know a renewal and could make unsafe decisions |
| Independent expiration on every replica | **Rejected**: differing clocks and partitions could create inconsistent owners |
| Permanent locks without renewal | **Rejected** for final design because disconnects cause indefinite blocking; useful only as an intermediate implementation milestone |

**Accepted cost:** renewing every selected element adds Raft log entries and increases message/write costs. In return, the system has straightforward safety under failover, with availability conditional on a majority. This is neither a multi-master offline editor nor a system with precisely timed lock expiry.
