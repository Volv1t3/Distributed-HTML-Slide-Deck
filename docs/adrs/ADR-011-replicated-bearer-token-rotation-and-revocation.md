# ADR-011 — Raft-Replicated Opaque Bearer Tokens, Atomic Rotation, and Revocation

- **Status:** Accepted
- **Date:** 2026-11-24
- **Stage:** E, authentication foundation
- **Related:** ADR-002, ADR-003, ADR-007, ADR-009, ADR-010
- **Implementation reference:** `Stage-E-Authentication-Implementation-Spec.md`

## Context

A token generated by the leader must remain verifiable after a leader failure. Replicating its raw bearer secret unnecessarily exposes the credential to every follower's disk, persisted log, debug output, and backups. A single SHA-256 digest of a **uniformly random, high-entropy** token is sufficient for verification without retaining the secret. Unlike human passwords, generated 256-bit tokens do not need a slow password KDF.

The application also needs explicit revocation and recovery when an `issue_access_token` command commits but the leader fails before returning the raw token to its client.

## Decision

### Token generation and record

1. On a valid password-authenticated login, the current leader generates **32 cryptographically secure random bytes** using `secrets`, exposes only an encoded token to the client, and computes its SHA-256 digest. No encryption key or IV is required: the token is not decrypted by replicas.
2. The leader proposes a typed `issue_access_token` command containing `user_id`, `client_id`, generated `credential_id`, `token_digest`, and other **non-secret** metadata. Only the digest is copied to the Raft log and durable FSM. The plaintext token lives temporarily in the proposing leader's **volatile pending-login response memory**.
3. The deterministic FSM maintains exactly **one active credential generation** for each bound `(user_id, client_id)`. Applying `issue_access_token` atomically replaces the previous digest/credential ID, clears a previous revoked state, and increments a per-client `credential_generation`. It does not require the previous token or a client-side compare-and-swap. Every replacement is serialized by Raft application order.
4. A `revoke_access_token` command, authorized for the authenticated user's own bound client for this phase, **targets an `expected_credential_id` and `expected_generation`**. When they match the current record, it atomically marks that credential revoked and advances its generation (or uses an equivalent tombstone). A delayed logout targeting an older generation must return `STALE_CREDENTIAL` rather than revoking a newer login. It must not delete the client binding or user account. Administrative revocation of other users belongs to the later sharing/administration design.
5. Token lifetime is **persistent across client restarts**. Baseline Stage E does not enforce clock-based expiration. Expiration is an explicit, future extension and must not be simulated with unsynchronized replica clocks in deterministic apply.
6. The leader returns `AUTHENTICATED` plus the plaintext token **only after** majority commitment, durable state-machine application, and successful association with the exact newly issued credential generation. A committed login's result record stores only safe fields and never the raw token.

### Failure, retry, and concurrency rules

7. If a login commits and its response is lost, a new leader may know the digest but **cannot reconstruct the token**. Therefore an exact replay that lacks the volatile secret must return a documented `REAUTH_REQUIRED`/`LOGIN_SECRET_UNAVAILABLE` outcome, not a fake success without a usable token. The client performs a fresh password-authenticated login with a **new request ID**. Its previous logical `client_id` and journal request IDs remain unchanged.
8. Within a single leader incarnation, repeated delivery of the **same** login request ID must not generate a different token/digest under that identity. The adapter associates the first generated token with the pending request until completion, or returns a deliberate reauthentication response. Replayed leader RPCs and request deduplication must not produce `REQUEST_ID_REUSE` merely because random bytes were regenerated for the same attempt.
9. On successful reauthentication, the fresh `issue_access_token` command atomically supersedes the previous token. The next response includes `credential_generation`. A client must not install a **late older** login response over a newer generation; if it holds a now-invalid token, it logs in again. Authenticate/rotate sequentially per client (no deliberate concurrent login requests in the baseline) and use bounded backoff rather than flooding a partitioned cluster.
10. For login issuance, the verifier check takes place on the leader outside deterministic Raft apply. During apply, validate account existence, stable client binding, unique credential ID, and canonical record format; the trusted leader's password-admission decision is an explicit trust assumption. Replicas do not recheck the plaintext password.
11. A leader must not answer credential-authenticated operations using stale or incompletely applied credential state. Every password or bearer admission completes a fresh quorum-confirmed Auth Admission Read and applies through that index before validation or stored-result disclosure. The election no-op establishes current-term commitment but is not, by itself, a fresh leadership proof after a later partition. An unready or isolated leader waits, redirects, or returns unavailable.
12. Normal protected commands carry a **non-secret credential reference**, not the bearer secret. At deterministic apply, verify that reference is still current for `(authenticated_actor_user_id, client_id)` and not revoked; otherwise the command is a committed deterministic denial with no business mutation. Compare securely supplied token digests with `hmac.compare_digest` at admission.
13. Password verification runs in a bounded background worker using a copied verifier and bounded password bytes. The worker never reads or mutates Raft state; the single node event-loop thread consumes its result and performs proposals and replies only if the captured leader term remains current. This preserves heartbeats, elections, and message processing while PBKDF2 runs and prevents a stale worker result from issuing a credential after step-down.
14. A bearer token is stored client-side only in an access-restricted, atomically replaced credential file outside the disposable cluster `run/` directory. Token rotation never rewrites the Durable Intention Journal or its request IDs.

## Why majority commitment is sufficient

For three voters, issuance is committed after two durably acknowledge the log entry, not after all three do. If n1 and n3 contain committed entry X and n1 crashes, lagging n2 cannot win an election against n3 on its older log; the new leader preserves X through Raft leader completeness. n3 may need to commit a current-term entry to learn/apply its committed prefix before using the token record. No second two-phase commit protocol is necessary.

## Sensitive-data and evidence rules

- Persist **only** `token_digest`, `credential_id`, `user_id`, `client_id`, `credential_generation`, `revoked`, and deterministic metadata needed by the state machine. Treat token digests as security-sensitive internal records even though they cannot be used as bearer secrets if the protocol never accepts a digest directly as a token.
- Never echo credential digests to clients or accept them as alternative bearer tokens. Require the **raw token** at the ephemeral transport boundary; the leader computes the digest.
- Never place raw tokens or passwords in `client_journal.py` append-only records, debug logs, request payload fingerprints, structured histories, or archived checker evidence. Tests should scan these artifacts for leakage.
- A success response to an older committed command might be retrievable under **newly valid authentication** as an idempotent dedup result; this must not reapply the command. A revoked token alone must not retrieve that result.

## Consequences

- Log entries and persisted snapshots contain no reusable bearer secrets; they still contain non-reversible security verifier material in plain JSON.
- Lost token responses require deliberate reauthentication, not a reversible token store or exact-ID token reconstruction.
- The client's persistent journal remains independent of token rotation.
- Issuance, revocation, and protected writes receive one total order across leader failover; credential validation at application prevents post-revocation mutation.
- There is no need for 2PC, distributed CAS, shared encryption keys, token IVs, database containers, or clock-based lease expirations.
- Persistent bearer tokens without idle or absolute expiration are an accepted classroom limitation, not production session-management guidance. Explicit revocation is the only Stage E invalidation mechanism; expiration remains future work.

## Alternatives considered

- Replicate plaintext bearer secrets: rejected due to unnecessary exposure.
- Persist encrypted tokens and distribute an encryption key: rejected because the replicas need only verifier digests.
- Locally revoke only on the leader: rejected because a replacement leader must inherit revocations.
- Require all voters to acknowledge issuance or use 2PC: rejected; Raft majority commitment already guarantees leader completeness.
- Store/reuse one raw token in replicated deduplication responses for perfect exact-ID login replay: rejected as contrary to the non-secret durable-state goal.
