# Stage E.A validation

Run the normal scenario from the repository root:

```sh
python3 scenarios/run_stage_ea.py --scenario stage_e_normal
python3 scenarios/run_stage_ea.py --scenario stage_e_rotation
python3 scenarios/run_stage_ea.py --scenario stage_e_failover
python3 scenarios/run_stage_ea.py --scenario stage_e_lost_login
python3 scenarios/run_stage_ea.py --scenario stage_e_partition
```

The runner refuses to start when `run/` already exists. It starts three local replicas, runs the scenario, copies its evidence into a uniquely named `historiales/<timestamp>-<scenario>/` directory, and shuts down the cluster even if an assertion fails. The Stage E archive includes each replica's actual `disk.json` Raft snapshot and log entries, plus `roles.log`, `events.log`, and all scenario JSONL outputs. The scenario's literal-secret scan runs before this copy. The existing starter `cluster.py down` also keeps its ordinary history archive.

The normal scenario logs in with the pre-provisioned Sofia fixture, then publishes a deck and exercises authenticated element and settings mutations. It checks a wrong editor session, stale element version, stale Deck Settings Version, and stale Slide Settings Version. Final reads and durable auth summaries must agree across all replicas.

The rotation scenario logs in twice with one stable client UUID. It checks that a repeated first login ID does not issue another credential, the older bearer is rejected after rotation, the newer bearer can edit, a stale revoke cannot invalidate it, and the current credential revokes once. An exact revoke retry and a fresh edit with the revoked bearer both fail admission. Phase-by-phase auth summaries record the credential generation and revocation state on all three replicas.

The failover scenario stops one follower before login, verifies the issuance entry is durable, committed, and applied on the issuing leader and the other voter, then stops that leader. It restarts the lagging follower with its disk intact so the up-to-date voter can win election, uses the issued bearer for protected writes on that replacement leader, and restarts the old leader. Final auth summaries compare the client binding, credential identity, generation, revocation state, and digest across all three replicas. Presentation settings and applied indexes must converge. The fault trace and election unavailability measurement remain in the same archive.

The lost-login scenario intercepts the committed HTTP response at the authenticated client's transport boundary. After the issuing leader and another voter durably apply the issuance, the scenario stops that leader and discards the response before `AuthenticatedClient.login()` can install the bearer. The client history records a failed delivery, and no credential file is created. After election, the same installation sends the old login ID to the replacement leader and receives `LOGIN_SECRET_UNAVAILABLE`; a new login ID reaches generation 2. A durable publication intention queued before login keeps its original request ID through reauthentication and commits with the new bearer. The scenario verifies the old digest is retired, all replicas converge, and the literal lost and replacement bearers are absent from the disposable run tree, including Raft disk snapshots and logs.

The partition scenario isolates the current leader as a one-node minority. Direct requests there cannot acknowledge login issuance, self-revocation, disclosure of a stored authenticated result, or a new protected settings write. The elected majority leader runs an overlapping write and revoke with the write first in Raft order. A second client demonstrates the reverse Raft order: a short outbound delay lets its revoke and write pass fresh admission before either commits, so the log applies revoke first and records `UNAUTHENTICATED` for the following write without advancing Deck Settings Version. After healing, the scenario compares all three replicas' auth summaries, selected durable request results, settings, and applied indexes. A sequential reference in `spec.py` replays committed non-secret issuance, revocation, and deck-settings commands and checks their durable outcomes in Raft order. The checker projection handles presentation operations; its audit retains the authentication exclusions.

The archive contains the redacted client history, checker projection and audit, checker result, manifest with a clean run ID, fault trace, credential-generation trace without bearer material, and separate latency buckets for login, token issuance, token revocation, successful authenticated edits, and committed authentication denials. Token issuance latency measures the leader's interval from `login_issuance_proposed` to `login_completed`; login and revoke latency measure complete client calls. Each bucket records p50/p95 and a comparison to the unchanged Stage D normal-run baseline. The baseline is the recorded `historiales/20261124-222700/stage_d_normal_metrics.jsonl`, preserved verbatim in `docs/stage-ea-stage-d-baseline.jsonl` (SHA-256 `007bd406ca3bcdea75ce09a2ba039de2a2520a1be4639133b8f8fab6e8bfe221`). It has nine quorum edits (p50 4.856 ms, p95 14.502 ms), but no login, issue, or revoke operation; those three Stage D comparison values are explicitly null. The Stage E edit populations differ from Stage D, so the comparison is descriptive. The checker projection excludes login, revocation, and explicit authentication admission denials; the audit names each exclusion and the independent committed-order reference checks the auth transitions. The scenarios scan the disposable `run/` tree for their literal test password and issued bearers before shutdown.
